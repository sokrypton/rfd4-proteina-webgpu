Operational guide for coding agents working in `rfd4p` (WebGPU implementation of `RosettaCommons/RFD4-Proteina`, inspired by `../localfold`).

## Architecture & Module Layout

1. **Plain ES Modules Only**:
   - All JavaScript files must be standard ES modules loadable directly by the browser without a bundler or compiler.
   - Always include explicit `.js` file extensions in relative `import` specifiers.
2. **Directory Structure**:
   - `shared/rfd4p/`:
     - `encoding.js` & `conditions.js`: 147-token `UNIFIED_ATOM37_ENCODING` vocabulary, atom37 layouts, and condition / CATH enums.
     - `pipeline/`: Pure-JS input transform pipeline (`buildBatch` in `pipeline/index.js`) with Zstandard `.cif.zst` frame decompressor (`zstd.js`), mmCIF/PDB/annotated-CIF parser + WL entity hashes (`cif.js`), YAML/JSON condition-spec & `sel(...)` query evaluator (`spec.js`), 3D/topological stereochemistry (`chirality.js`), token bond graph & BFS path lengths (`bonds.js`), and validation transforms (`transforms.js`).
     - `features.js`: Upstream feature factories (`trunkSeqFeatures`, `trunkCondFeatures`, `pairFeatures` with static cache, `pairCondFeatures`).
     - `flow.js` & `partial.js`: Flow-matching schedules (`scheduleTsrSafe`, `noiseSchedule`, `recycleDepths`), Euler/SDE `simulationStep`, partial diffusion (`corruptBatch`, `buildPartialSchedule`), and inverse folding (`RESAMPLED_FORWARD_MARGINAL`).
     - `output.js`: Rectangular Hungarian linear sum assignment (`linearSumAssignmentMaximize`), unindexed motif insertion (`buildPredictedInsertionMapping`), internal-coordinate group grafting (`insertInternalCoordConditionedGroups`), input-frame Kabsch alignment (`alignAtomsToInputFrame`), `processSampleToAtoms`, and `toCifString` / `toPdbString`.
     - `safetensors.js` & `presets.js`: Zero-copy `parseSafetensors`, streaming + Cache API `fetchSafetensors` and `fetchShardedWeights` (keeps the int8 shard bytes; each tensor's `.data` decodes on read, so read large weights once, at GPU upload), and 10 interactive benchmark presets (`RFD4P_PRESETS`).
   - `cpu/rfd4p/`: Deterministic float32 CPU reference implementations (`trunk.js`, `decoder.js`, `encoder.js`, `reference.js`).
   - `webgpu/rfd4p/`: Recorded-command-list WebGPU engine (`engine.js` with `64x128` and `32x64` bank-conflict-free `vec4` GEMMs, `16x16` `triGate`, 64M-float triangle chunking, and FP16 weight packing), shared token blocks (`blocks.js`), `Rfd4pTrunkGpu` (`trunk.js`), `Rfd4pDecoderGpu` (`decoder.js`), `Rfd4pEncoderGpu` (`encoder.js`), and `Rfd4pGeneratorGpu` (`generate.js`).
   - `webgl/rfd4p/`: the fallback for browsers without WebGPU (Safari before 26, older Chrome): `gl.js`, a small WebGL2 tensor library (flat RGBA32F textures 3072 texels wide, so no row of the model's widths wraps; float16 weights; one fragment = one texel of 4 outputs; long draws split into bands; `readAsync` waits on a fence so the page stays responsive), and `model.js`, `Rfd4pModelGL`: the trunk, decoder and encoder as the CPU reference computes them, function for function (the big matmuls read packed halves, RGBA32UI with 8 float16 values a texel, so a 4x4 block per fragment over four render targets reads half the texels: 2x on an M2; their inputs are packed by their producers (pair norms, the pair transition's hidden layer) or on the fly, weights once; the triangle contractions are one batched packed matmul over the channels, x_c = A_c B_c^T, after a channel-major transpose (k padded to 8, i and j to 4), then gathered back; the triangle update's gated projections one fused kernel; residual adds and gates fused into matmul epilogues (`resid`); outputs that may be float16 (gates, the pair transition's hidden layer, z's recycle delta) from a 4x8 block written as packed halves (32 values a pixel, the 64-byte budget) and repacked a texel at a time; norm statistics in one walk of the row (`_normFast`). The matmuls are bound by texel fetches (a probe of the same loop: fetches alone 10.9 ms of 12.5, arithmetic alone 3.9), and the fetches per multiply-add are set by the outputs a fragment may write, so a WebGL2 matmul has a ceiling here near 700-800 GFLOP/s against WebGPU's shared-memory tiles; draws split into bands only when very long. The tensor pool is keyed by format: a packed texture handed out as a float one was a silent wrong answer. Tried and slower or no better on an M2 (`tools/gpu/bench-webgl.js`): 8-row blocks over 8 targets, float16 targets, unrolling, mediump products, explicit dots vs vec4*mat4, blitting planes instead of a repack pass). `generateRfd4pCpu` (now with early stop, as WebGPU's generator) runs on it through `opts.kernels`. Checked against the PyTorch oracle (`npm run check:webgl`: trunk at full recycle depth ~2e-4 relative RMS, decoder ~3e-5, encoder ~9e-4). The app picks it when there is no WebGPU device and WebGL2 can render to float textures (badge "WebGL2"; `?gl=1` forces it where WebGPU exists, for testing); refolding (LocalFold) stays WebGPU-only (`noRefold`). Speed (M2, per recycle cycle of a warm depth-6 call, as `check-trunk.js` reports WebGPU's `perPass`: `check-webgl.js --depth=6 --warm=1 --reps=3`, divided by 6): ~279 ms at n = 100 and ~1.04 s at n = 208: 0.97x and 0.90x WebGPU in stock Chrome measured back to back (286-288 / 1159-1161 ms), 2.1x and 2.0x WebGPU with Chrome's experimental WebGPU (135 / 538 ms). A whole 60-step design at n = 208 (`check-webgl --parts=generate --case=ppi_pdl1`, recycling included): 256 s, stock WebGPU half 275 s run straight after (`check-generate --half=1`), 0.004 A from the oracle against WebGPU half's 0.010; at n = 100 (`uncond_short`) 53.5 s against 66 s, 0.042 A against 0.040; sm_sam (n = 181) 186 s against 196 s (float32 z: 222 s). Long runs vary with the machine's heat by 10-15%: compare back to back. The largest single gain came from narrow textures (TW 3072 -> 384 texels: 2.35 -> 1.47 s at n = 208), cache locality across a GPU tile; `linear` makes its output only on the paths that write one. Then: the pair features' Cα distance bins added on the GPU to a projection of the rest kept from a job's first step (`pairDistsOnGpu`, as WebGPU does; no 22 MB upload and n^2 x 128 x 384 matmul a step), the attention pair biases of the layers that read one z as one matmul over z with the RMSNorm folded in (`_pairBias`), every layer's cond-only linears in two matmuls (`_condProj`), cycle 0's zero recycle terms skipped, feature rows padded to 32, token matmuls ordered row block fastest (`linear4x4pk-cm`), texel-wise pair write; around the triangle contraction, the gated projections computed in rows i * Kp + k and written transposed (a channel's 8 k are two texels for the transpose) and the gather writing four j-planes that the LayerNorm after it reads (`jplanes`); 4 x 8 outputs left as planes for a reader that takes them (`linear` 'planes': the transition's hidden layer as the next matmul's x, the triangle gate in `_repackResid`); z and the triangle contraction's result in float16 (`zHalf`, `xHalf`, as WebGPU's half mode holds them), which needed float16 render targets written rounded to nearest (`gl.js` `R16`): the conversion on writing truncates on an M2, and truncation's bias added up (z in float16 lost 6e-3 relative on motif_idx_1prw, 3e-4 rounded, as float32; a whole sm_sam design now ends exactly where WebGPU half's does, 1.67 A from the float32 oracle, 6 residues changed, a divergence of float16 z itself: float32 z gives 0.017 A); LayerNorms in front of a 4 x 8 matmul that reads z's planes folded into it (`_lnFold`: W' = W diag(w), the mean's term from rowsum(W'), only a statistics pass: the transition's and the recycle's); z held as packed planes in the 4 x 8 matmul's output layout (`_toZPlanes`, `zPlanes`: a residual update writes the new z in its epilogue, with no repack pass, and norms and the pair bias read half the texels); the token block fused (`_adaLNFused`, `_rowReader`, `_scaleAdd`, q/k/v/g split from the matmul's planes, SwiGLU packed from its planes) and the q/k RMS norms folded into the attention scores (`_attnFolded`); the pair write never materialised (`_pairWriteView`: the norm and the residual that read it add the outer product as they read); the heads drawn together and waited for once; to_qkv and to_g one matmul (`_stacked`); split K for token matmuls with few fragments (`linear4x4pk-cm-sk`). What a kernel costs in a real pass: `--skip=<regex>` leaves its draws out (wrong results, honest timing; the per-draw `--profile=1` syncs inflate short kernels several-fold). Tried and no faster: the output planes' texture width (48 to 768 texels: 1.48-1.55 TFLOP/s on the 4 x 8 matmul either way; which fragments run together is not this path's limit, unlike WebGPU's); a folded norm's statistics gathered in the matmul's own row walk (WebGPU's fused input norm: 1.07x slower, every column block repeats them); 2 x 2 quads of fragments sharing their fetches through derivatives (dFdx / dFdy are fine-grained here, so a fragment can read its neighbour's values: 6 texel reads per 256 multiply-adds, but 3.4x slower, `bench-webgl --quad=1`); the 4 x 8 block for token matmuls (fewer fragments at n = 100); fence polling by message-channel yields; an 8 x 8 block over eight packed targets (128 bytes a pixel: 2x slower than 4 x 8); norm statistics split over several fragments a row; weights as uniform buffers or constant-indexed uniforms (0.07-0.65 TFLOP/s against 1.3 from textures: ANGLE's constant buffers); the gated projections written straight into the batched matmul's channel-major layout (2.2x slower: neighbouring fragments then share no input rows). A microbenchmark that redraws into the same targets measures one draw, not several: the tiler's hidden-surface removal culls all but the last opaque full-screen draw of a render pass.
   - `web/`: Interactive browser studio (`index.html`, `web/app.js`, `web/studio-api.js`, `web/studio/`, `web/examples/*.cif.zst`) embedding the `nvidia/rfd4-proteina-zerogpu` / `AtomWorks Studio` interface (Mol* WebGL 3D viewer, sequence dock, condition popovers, live trajectory playback, and PDB/mmCIF/ZIP export) backed 100% client-side by WebGPU.
   - `web/design-spec.js` (pure: task, chain roles, lengths and contig read from a document's conditions; tested in `test/design-spec.test.js`) and `web/design-panel.js` (start screen, Design panel, guided set-ups, simple/advanced switch). The panel lists each chain piece by piece in contig order (`designSpec(...).chains[].pieces`): `kept` (with a keep mode from `KEEP_MODES`: all, sequence, backbone, side chains, shape only; `anywhere` when unindexed; `source` when a set-up renumbered it), `designed` (in place) and `new` (a length range). Chains are grouped by where their coordinates come from (`_sourceGroups`: "PDB 1QJG", "PDB 5O45 chain A", "Nanobody (VHH) example"), one muted caption per source; clicking a caption opens the + pdb form to replace that source's chains (the new structure is merged in first and the old chains removed after, so a one-chain example can be replaced; a Replace button beside it was tried and taken out as too busy), and a × beside it, shown while the caption is pointed at, removes that source (the last one left is Clear); chains are listed in the job's order (the sequence bar's, which is the order they were added), chains made here (+ seq, + lig) uncaptioned in place. Each piece is a sub-card in its chain (chain letter on the left; the chain's × there once it has more than one item), residues (or a new piece's length) on the left and its state on the right ("A17–131 · fixed · 3 hotspots", "H99–109 · designed", "50–120 · new"), its own × to remove it; a "+" between sub-cards adds new residues there, or, in a chain from a PDB entry, residues of the entry. Every option in the popups is fixed or free (free: the model decides; the internal values stay 'designed' and 'anywhere'), and every list ends with "free", Shape, Exposure, Interaction and Fold included; a ligand's pose is its Structure too. A residue popup (a sub-card's, or residues picked in the viewer or the sequence bar) shows, in front, its residue range (a sub-card's), Structure (fixed, rigid, free) with the Atoms it holds (all, backbone, side chains, or named: "CG, OD1"), Sequence (fixed, free) and Position in chain (fixed, free: an unindexed residue), with Structure and Sequence both free Length in Position's place, and a sub-card's Hotspots, the rest under More (`_moreFold`: Shape, Exposure, Interaction, and a sub-card's Keep only); there are no one-click buttons (they set four things at once and could not say "structure fixed, sequence free"). A sub-card's click also selects its residues in Studio while its popup is open (`_selectFromCard`, not the viewer's popup). Residues typed outside a piece's reach name the piece that holds them, with a link to open it ("B51 is in B10–138"). A sub-card's Residues take one range or several, as from – to boxes per range like a new piece's Length (`_rangeBoxes`, over the hidden text field the popup reads, "1–40, 60–115", and the crop bar writes; + adds a range, × drops one); once narrowed, Rest says what happens to the piece's residues outside them (removed, the default; free; unchanged, for changing part of a piece), the gaps between ranges are free, and Between gives them a length range, turning each into new residues (so a fetched chain is cut to a domain, or to two regions with a variable linker, in one popup); a Length other than the residue count turns them into new residues (`/segments/replace`), and the document remembers the residues they replaced (`segmentOrigins`, this page only; `segmentOrigin`, `restoreSegment`, `/segments/restore`; `test/segment-restore.test.js`): the new-residues popup then shows "was 7" beside Length and a Structure and Sequence, and the old count, or a fixed or rigid Structure or a fixed Sequence, brings them back in place with their coordinates and conditions, in one Undo; with partial diffusion ticked, its warning about new residues offers the same for all of them ("Back to the residues they replaced"), since partial diffusion starts from coordinates. A piece of a loaded chain has a crop bar under its Residues (`_cropBar`): the chain as it was loaded (`chainSources`, kept by a plain structure's `StudioDoc` and carried by `combine` and a chain rename; `sourceResidues`), the piece's ranges on it, the chain's other residues muted, a handle at each end; dragging in crops (Rest), dragging out brings residues back, up to the neighbouring piece and never past new residues (`restoreFromSource`, `/residues/restore`: as loaded, then given the popup's settings, those in gaps free). It only edits the Residues field, so typing a range past the piece does the same. As the ranges change (dragged or typed), the structure previews them (`_previewCut`): residues to be cut nearly vanish (`setHighlight('cut', …)`), those to be freed fade as free ones do, and only the residues kept stay selected; closing the popup clears it. Opening a sub-card's popup also brings its residues to the middle of the view, the zoom kept (`centerOn`, fork 12c2b78). During a run and on a finished design, the held coordinates of a motif are drawn as a grey reference (`buildMotifOverlayAtoms`, `motifSideChainAtoms`): residues placed anywhere always, residues held in place only when they are a quarter of their chain or less (`isSmallMotif`: 1QJG's three, not a kept domain extended by new residues, which would only be drawn twice). Residues the model rebuilds (no atom held, not rigid) are faded in the input structure (`setHighlight('free', …, { transparency })`, fork f7a02ee), except with partial diffusion ticked, where they are its starting point. Hotspots (the chain's, from any of its pieces; a residue may name its atoms, "A56(CG,OH)", `parseResidueList`) and, under More, Keep only (the motif set-up, `/segments/scaffold`; the residues are kept in the order typed, "A38, A14, A99" reorders the motif and renumbers the chain as AtomWorks does, `_orderMotif`, each kept residue keeping its source ("A38", `annotation_src-component_1_atom`, display only: the pipeline rewrites it) so the card still names it by the entry, and so does its popup (Residues reads "A38", with no crop bar: its numbering in the new chain would not match the card); the kept residues take the popup's properties, so trimming an antibody chain and making it "rigid" is one popup). "Rigid" is one rigid group per source structure (`/internal-coords` `group_id`, `_rigidGroup(chain)`: chains from the same entry share a body), so an antibody's heavy and light frameworks keep their pairing and move as one, as upstream's current antibody example (Studio 0.0.6, MZB1/adalimumab Fv) and the model repo's VHH inputs are set (the Oct 19 example the demo Space ships had them as two bodies, since replaced), a framework split by CDRs moves as one, and chains from different entries move apart, and its saved targets are cleared (`/internal-coords/clear-targets`): the pipeline centres the body and turns it at random when the job is built (`materializeInternalCoords`), as AtomWorks does and the bundled examples are saved. A residue fixed "anywhere" with only some atoms held keeps only those atoms' coordinates, held atoms first in the residue (`/coordinates/clear`; a token is read from its first atom), as an enzyme benchmark's catalytic tips are given. Residues can be brought back from their source entry next to their neighbours (`/residues/insert`, `insertResiduesFrom`: one Undo, peptide and new-residue bonds rebuilt, an ordered motif's chain renumbered; `test/residue-insert.test.js`); the "+" between pieces of a chain from a PDB entry uses it (`_slotPop`, `_bringBack`): it offers new residues (a length) or residues of the entry ("A14", "A45–52"), placed where the "+" was (`at_atom`, `before`; out of source order, as in a motif, the chain is renumbered and the residues keep their source names), so a motif residue removed by mistake comes back in place; a chain not from an entry adds new residues straight away. The chain letter opens the chain's popup: its name (`/chains`), its place in the job (`/chains/order`), which the model reads (chain and molecule ids, noise draws), and a fold for it (CATH, `cath_label`, `_foldField`: the chain popup's labels the whole chain, the new-residues popup's only those new residues, so one chain can hold domains of different folds, 6MRR kept and a β-barrel built onto it; a new block shows its fold, "β-barrel · new"; named folds such as ferredoxin-like 3.30.70, Rossmann-like 3.40.50, helix bundle 1.10, or any code; a new chain's is set on its new residues, which each take it; also in the new-residues popup, where a new chain is laid out). Superposition (`superimposeCoords3D`) is a rotation, never a reflection (`test/handedness.test.js`): it used to mirror whenever its eigenvectors came out left-handed, and a design with nothing held in place, aligned onto its first (noise) frame, was then shown as its mirror image, every helix left-handed, about half the time; the model's own estimate was right-handed throughout. A residue placed anywhere is read against all its atoms (`heldAtomsOf`, `allHeavyNames`), since only its held atoms keep coordinates, so its row names them ("A250 CG, OD1 fixed · position free"); a glycine joins a named-atoms or side-chain run it sits in, and an interaction is asked of each residue's side chain, or its CA when it has none. Under More, residues can also be asked a Shape (secondary structure as DSSP letters, H helix, E strand, C loop: cards show the letter, "6 · E · new", the popup the letter and word), an Exposure (RASA: buried, intermediate, exposed) and an Interaction their side chains (or the atoms named) should make (H-bond donor/acceptor, salt bridge, π-stacking, π-cation, hydrophobic, metal-coordinating) (`_extraFields`); new residues take Shape and Exposure. These were Advanced-editor only; pieces split where they differ and rows name them ("A20–30 free · H"). Residues selected in the viewer or the sequence bar open a shorter popup for the selection (`_renderPop`): Structure and Sequence ("mixed" where the selected pieces differ, left as each piece has it), Length for one free stretch, Hotspot and Include checkboxes (unticked, the selection is taken out of the job on Apply) and a ligand's Structure, with Atoms, Position, Shape, Exposure and Interaction under More (a pick shows little at first), so fixed regions are grown, shrunk, freed or cut from the structure itself (a motif by hand: pick the residues around it, Structure and Sequence free, a Length); several pieces change in one edit (`_applyPieces`), one Undo. Ligands: Structure fixed or free, swap. New residues: Length, Shape, Exposure and the chain's Fold. More folds only four rows or more; fewer are shown as they are (`_moreFold`). Popups close with the × in their title (top right; a viewer pick's also lets go of the selection), Escape or a click outside other than in the viewer (a row's popup stays while the structure is turned; a click there picks nothing new while it is open), and move by their title bar (`_movable`): once moved, every popup opens where the last was left, kept on screen, until a reload (`popSpot`); Apply sits at the bottom, always in sight. A "+" sits between any two pieces and at both ends, new residues included, so a free chain is built as blocks of different lengths and shapes (20 H · 6 C · 20 E). New residues inserted inside a chain do not renumber it: with no numbering gap the placeholder takes the residue before's number plus an insertion code (`insertSegment`, "40A"), and `realizeExpandableSegments` numbers past it, so the batch and the design are numbered exactly as the old renumber-the-rest rule made them (`test/insert-numbering.test.js`). A design therefore numbers residues after an insertion further along than the input; hotspots on designs are matched through each sample's batch atoms for that reason. A binder's target is set up as upstream recommends (RFD4-Proteina's protein-binder task and `condition_spec_ppi.yaml`; an author's note with the supplementary figure: absolute target coordinates give more binders that copy the target): its backbone one rigid group with internal coordinates, its sequence fixed, its side chains free, hotspots kept (`_asLoaded`, `_makeTargets`: on + seq beside chains still as loaded, on + pdb beside a chain being designed; chains set up otherwise are left alone; the binder example gets it through + seq, the nanobody's PD-L1 in its recipe). With nothing held in place, upstream leaves a design in the model's frame; the page lays it on its rigid target as loaded (`processSampleToAtoms({ inputFrame: true })`, `alignOntoRigidGroup`: the group on a chain with hotspots, else the largest), live frames and designs alike (the Cα trajectory still follows the run's first frame). A rigid residue counts as held when roles are read, so a rigid target still reads "Binder design". On desktop Chrome without subgroup matrices, the speed notice sits under Generate (`_initSpeedHint`; Copy address, Not now) and each design's status line repeats "up to 1.5× faster" until it is dismissed. Thinking sits under Generate and defaults to none, for speed (upstream's default is medium, `inference.yaml`; about 3x the passes). A plain structure (PDB ID, optionally with the chains to keep, "1J79 A C E", which keep the ligands the entry files under them, `pdbx_nonpoly_scheme.pdb_strand_id`, or a ligand by its code, "9FJX B LVY", `namedAtoms`; a file; "+ pdb") opens with everything fixed, without buffer ions (NA, CL, on top of AtomWorks' additive list), without the residues the entry did not resolve (`removeUnresolvedResidues`: an unmodelled end or loop would otherwise come in as "sequence fixed" pieces the model builds; the example recipes keep them, `keepUnresolved`, as upstream's examples were set up) and with its ligands' formal charges from the CCD (RCSB entries list their components' atoms without charges, `componentsNeedingCcd`); a prepared document drops the file's text (`rawCif`), so its CIF, for the viewer and for a run, is the prepared one from the first frame (`StudioDoc`, rcsb preset; `test/fetch-defaults.test.js`), so a set-up starts from what was loaded and marks what to design; Keep only takes the popup's Structure, Atoms and Position (CG, OD1 + anywhere is an enzyme site), and ticking partial diffusion with nothing designed frees every chain. "Blueprint" draws a ferredoxin-like fold as blocks (β 6 · loop 3 · α 14 · loop 3 · β 6 · loop 3 · β 6 · loop 3 · α 14 · loop 3 · β 6) from the bundled empty chain (`start`, `blocks` steps; no download); a design follows it (helix blocks Cα i→i+3 5.1 Å and right-handed, strands 10 Å). The start screen starts a job from its parts with the design view's own row, + seq (a free chain of 60–100, from the bundled empty chain), + pdb (the PDB ID / file form) and + lig (a ligand by its code), each opening a new document (`_startNew`), and under it the Examples (a heading, not a question: nothing there has to be picked). Start-screen examples are recipes (`TASKS[].recipe`): each fetches its PDB entry (5O45, 1XVA, 1QJG, 1J79, 1N8Z, 4Z18 + 3EAK, 2KL8, in label numbering; an entry's chains come from its first biological assembly that has them, `_openEntry`) and reproduces the bundled Studio example of the same name in everything the model reads (batch features compared tensor by tensor; the motif is identical, the antibody too but for two deliberate changes, its heavy and light chains one rigid body and their fold Ig-like (CATH 2.60.40, recipe `{ chain, fold }`), as upstream's examples now are; both 2KL8 examples keep residues 1–79 (all of it but the His tag), where the bundled file drops 8–27, a bug in it; the rest differ only where the bundled file's coordinates did not come from the deposited entry: the binder's rebuilt side chains, the SAM conformer, the nanobody framework's saved orientation, and 0.001 Å rounding in the enzyme) and builds the set-up with the card's own controls in a session Studio does not show (`_buildRecipe`: `buildSession`, whose edits go straight to `handleStudioApiRequest`, so the viewer is not redrawn per step; popups hidden by `body.rfd4p-building`), then opens it once, finished, with no Undo history; if an entry cannot be fetched or a step fails, nothing opens and the start screen says why (no stand-in; "Protein from scratch" is the bundled example by design). Source captions read "PDB 5O45 · A" (entry and its chains in the job; the entry's `_struct.title` when pointed at). Designs and live frames are put back in the input's frame (the pipeline centres the conditioned coordinates for the model and records `center_shift`; `processSampleToAtoms` adds it back after aligning), so a fetched target does not jump when a run starts. During a run the hotspot highlight follows the job's numbering (`app.liveHotspotKeys`, res_id past any new residues), since live frames are numbered that way, and the viewer repaints it on every live frame (fork: Mol* keeps paint as atom positions, and a frame's designed residues change atom count from step to step, so paint carried over slid onto other residues; the viewer's `data-highlight-residues` says what is painted). Otherwise hotspots are highlighted in the viewer by `auth_seq_id`, which is how the document's CIF numbers residues for Mol* (a fetched entry keeps its authors' numbering there; `res_id` is the label numbering). There are no separate guided set-ups; partial diffusion is a line under the run settings' More settings, which open whenever it is turned on, so it is never on out of sight (one control: the checkbox and its noise %, 40% by default, `partial_trajectory_fraction_steps` 0.4 as upstream's Space runs its partial-diffusion example). A job whose every chain keeps its backbone with its sequence free (the card's "Redesign sequence", `task.key === 'inverse'`) runs the inverse-folding sampler (`resampled_forward_marginal`), as the Space does for that task (`generation=inverse_folding`): the backbone comes back as given (Cα within 0.02 Å), only sequence and side chains sampled. The encoder treats an atom without coordinates (a side chain an entry did not resolve) as absent (`encoderSeqFeatures`), or its NaN reached every latent and partial diffusion of such an entry (6MRR) gave a design with no atoms. Hotspots are a chip on a kept piece (`parseResidueList` / `formatResidueList`). Ligands are added ("+ lig") or swapped (a ligand's Edit menu) by their CCD code: `web/ligand-ccd.js` turns the dictionary entry's ideal coordinates into a one-residue mmCIF, merged in with its pose free. "+ seq", "+ pdb" and "+ lig" add a designed chain, chains from a PDB entry or file, or a ligand; merged in as kept chains through `/combine` (a source caption replaces that source instead), so an example is edited the same way a set-up is built from scratch. The panel edits documents only through `window.__rfd4pMutate`, so Undo and Studio refreshes work as for Studio's own edits.
   - **Chains are edited as plans** (studio-api.js `chainPlan`, `rebuildChain`, `previewRebuild`; `/chains/rebuild`; `test/chain-plan.test.js`, `test/chain-links.test.js`). ## WebGPU & Numerical Invariants

1. **Differential Verification**:
   - Every WebGPU kernel and network layer in `webgpu/rfd4p/` must be verified against the PyTorch oracle dumps and `cpu/rfd4p/` via `npm run test:gpu` (`DISPLAY=:99 node tools/gpu-chrome.mjs tools/gpu/check-rfd4p.js`).
2. **No `O(L^3)` Materialization**:
   - Triangle multiplicative updates (`tri_mult_out`, `tri_mult_in`) contract over `k` inside registers in the WGSL shader and never allocate `L x L x L` buffers.
3. **Guarded 2D Workgroup Dispatches**:
   - Any folded 1D workgroup index (`wid.x + wid.y * 65535u`) must check `< totalWorkgroups` before reading or writing storage buffers.
