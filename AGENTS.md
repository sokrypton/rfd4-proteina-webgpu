# AGENTS.md

Operational guide for coding agents working in `rfd4p` (WebGPU implementation of `RosettaCommons/RFD4-Proteina`, inspired by `../localfold`).

## Architecture & Module Layout

1. **Plain ES Modules Only**:
   - All JavaScript files must be standard ES modules loadable directly by the browser without a bundler or compiler.
   - Always include explicit `.js` file extensions in relative `import` specifiers.
2. **Directory Structure**:
   - `shared/rfd4p/`:
     - `encoding.js` & `conditions.js`: 147-token `UNIFIED_ATOM37_ENCODING` vocabulary, atom37 layouts, and condition / CATH enums.
     - `pipeline/`: Pure-JS input transform pipeline (`buildBatch` in `pipeline/index.js`) with Zstandard `.cif.zst` frame decompressor (`zstd.js`), mmCIF/PDB/annotated-CIF parser + WL entity hashes (`cif.js`), YAML/JSON condition-spec & `sel(...)` query evaluator (`spec.js`), 3D/topological stereochemistry (`chirality.js`), token bond graph & BFS path lengths (`bonds.js`), and validation transforms (`transforms.js`).
     - `features.js`: Upstream feature factories (`trunkSeqFeatures`, `trunkCondFeatures`, `pairFeatures` with static cache, `pairCondFeatures`).
     - `flow.js` & `partial.js`: Flow-matching schedules (`scheduleTsrSafe`, `noiseSchedule`, `recycleDepths`), Euler/SDE `simulationStep`, partial diffusion (`corruptBatch`, `buildPartialSchedule`), and inverse folding (`RESAMPLED_FORWARD_MARGINAL`).
     - `output.js`: Rectangular Hungarian linear sum assignment (`linearSumAssignmentMaximize`), unindexed motif insertion (`buildPredictedInsertionMapping`), internal-coordinate group grafting (`insertInternalCoordConditionedGroups`), input-frame Kabsch alignment (`alignAtomsToInputFrame`), `processSampleToAtoms`, and `toCifString` / `toPdbString`.
     - `safetensors.js` & `presets.js`: Zero-copy `parseSafetensors`, streaming + Cache API `fetchSafetensors` and `fetchShardedWeights` (keeps the int8 shard bytes; each tensor's `.data` decodes on read, so read large weights once, at GPU upload), and 10 interactive benchmark presets (`RFD4P_PRESETS`).
   - `cpu/rfd4p/`: Deterministic float32 CPU reference implementations (`trunk.js`, `decoder.js`, `encoder.js`, `reference.js`).
   - `webgpu/rfd4p/`: Recorded-command-list WebGPU engine (`engine.js` with `64x128` and `32x64` bank-conflict-free `vec4` GEMMs, `16x16` `triGate`, 64M-float triangle chunking, and FP16 weight packing), shared token blocks (`blocks.js`), `Rfd4pTrunkGpu` (`trunk.js`), `Rfd4pDecoderGpu` (`decoder.js`), `Rfd4pEncoderGpu` (`encoder.js`), and `Rfd4pGeneratorGpu` (`generate.js`). Subgroups are optional: on a device without them (Safari on an iPad: f16, no subgroups; the first Generate failed there, every kernel's `enable subgroups;` refused) `subgroupMode` is 'shared' with `none`, which takes the directive out and reduces each 32-lane row in workgroup memory, the GEMM takes its plain variant (`baseline`, no shuffles), and the GEMVs keep their kernels (their sums are `r32Add`). Checked with `RFD4P_NO_SUBGROUPS=1` (tools/gpu-chrome.mjs requests the device without them): check-rfd4p allOk, a half design 0.035 Å Cα from the oracle (0.031 with subgroups), 35.7 s against 34.7 at n = 100 on an M2. A recording that throws is not kept (`record`, `test/record-retry.test.js`), or the next call ran programs never made. Firefox (wgpu/naga: f16, no subgroups) takes the same path, and its compiler refuses the f16 width bitcasts (`bitcast<vec2<f16>>(u32)`: "ShaderModule with 'rfd4p.gemm-...' label is invalid"), so the engine compiles every kernel through LocalFold's `compilerText` (`webgpu/localfold-runtime.js`, vendored: `localfold.json` `runtime`), which spells them with unpack2x16float / pack2x16float there, unrolls short loops and cuts workgroup arrays over 8 KiB (naga runs both slowly; fp32 trunk 2.2 s a pass before, half 180 ms after), and `requestWebGpuDevice` is LocalFold's `requestAlphaFoldDevice` (compiler recorded, Firefox's 100 ms completion tick pumped). `LOCALFOLD_GPU_FIREFOX=1` runs any GPU tool in Firefox (LocalFold docs/FIREFOX.md): check-rfd4p --half=1 allOk, a half design 0.031 Å Cα in 33 s, the page's design and OpenBind-0 refold (check-refold) on WebGPU FP16.
   - `webgl/rfd4p/`: the fallback for browsers without WebGPU (Safari before 26, older Chrome): `gl.js`, a small WebGL2 tensor library (flat RGBA32F textures 3072 texels wide, so no row of the model's widths wraps; float16 weights; one fragment = one texel of 4 outputs; long draws split into bands; `readAsync` waits on a fence so the page stays responsive), and `model.js`, `Rfd4pModelGL`: the trunk, decoder and encoder as the CPU reference computes them, function for function (the big matmuls read packed halves, RGBA32UI with 8 float16 values a texel, so a 4x4 block per fragment over four render targets reads half the texels: 2x on an M2; their inputs are packed by their producers (pair norms, the pair transition's hidden layer) or on the fly, weights once; the triangle contractions are one batched packed matmul over the channels, x_c = A_c B_c^T, after a channel-major transpose (k padded to 8, i and j to 4), then gathered back; the triangle update's gated projections one fused kernel; residual adds and gates fused into matmul epilogues (`resid`); outputs that may be float16 (gates, the pair transition's hidden layer, z's recycle delta) from a 4x8 block written as packed halves (32 values a pixel, the 64-byte budget) and repacked a texel at a time; norm statistics in one walk of the row (`_normFast`). The matmuls are bound by texel fetches (a probe of the same loop: fetches alone 10.9 ms of 12.5, arithmetic alone 3.9), and the fetches per multiply-add are set by the outputs a fragment may write, so a WebGL2 matmul has a ceiling here near 700-800 GFLOP/s against WebGPU's shared-memory tiles; draws split into bands only when very long. The tensor pool is keyed by format: a packed texture handed out as a float one was a silent wrong answer. Tried and slower or no better on an M2 (`tools/gpu/bench-webgl.js`): 8-row blocks over 8 targets, float16 targets, unrolling, mediump products, explicit dots vs vec4*mat4, blitting planes instead of a repack pass). `generateRfd4pCpu` (now with early stop, as WebGPU's generator) runs on it through `opts.kernels`. Checked against the PyTorch oracle (`npm run check:webgl`: trunk at full recycle depth ~2e-4 relative RMS, decoder ~3e-5, encoder ~9e-4). The app picks it when there is no WebGPU device, or one without `shader-f16` (the model's kernels are float16) and WebGL2 can render to float textures (badge "WebGL2"; `?gl=1` forces it where WebGPU exists, for testing); refolding runs on LocalFold's own WebGL2 fold there (`refoldDesign({ backend: 'webgl2' })`, LocalFold branch `opus-55-opt`, pinned in `localfold.json`: AF3 and OpenBind-0, ~3-4x slower than its WebGPU fold, Cα 0.02-0.15 Å from it; the fold, its diffusion head and its weight upload are generators awaited a piece at a time, since every WebGL context's sync call, the viewer's included, waits behind what the fold has queued: the longest stall of a page refold ~150 ms, `check-refold.js --gl=1` reports it; it runs in Safari 16.3 too: no Float16Array (LocalFold's weight reader widens float16 from its bits) and no OffscreenCanvas WebGL2 (a document canvas), a 10-step refold 24 s, 15 s once its ~30 shader programs are built (light kernels share programs; the first fold's dry run finds them and links them while the fold waits on the GPU), one ~0.5 s stall as it starts). Speed (M2, per recycle cycle of a warm depth-6 call, as `check-trunk.js` reports WebGPU's `perPass`: `check-webgl.js --depth=6 --warm=1 --reps=3`, divided by 6): ~279 ms at n = 100 and ~1.04 s at n = 208: 0.97x and 0.90x WebGPU in stock Chrome measured back to back (286-288 / 1159-1161 ms), 2.1x and 2.0x WebGPU with Chrome's experimental WebGPU (135 / 538 ms). A whole 60-step design at n = 208 (`check-webgl --parts=generate --case=ppi_pdl1`, recycling included): 256 s, stock WebGPU half 275 s run straight after (`check-generate --half=1`), 0.004 A from the oracle against WebGPU half's 0.010; at n = 100 (`uncond_short`) 53.5 s against 66 s, 0.042 A against 0.040; sm_sam (n = 181) 186 s against 196 s (float32 z: 222 s). Long runs vary with the machine's heat by 10-15%: compare back to back. The largest single gain came from narrow textures (TW 3072 -> 384 texels: 2.35 -> 1.47 s at n = 208), cache locality across a GPU tile; `linear` makes its output only on the paths that write one. Then: the pair features' Cα distance bins added on the GPU to a projection of the rest kept from a job's first step (`pairDistsOnGpu`, as WebGPU does; no 22 MB upload and n^2 x 128 x 384 matmul a step), the attention pair biases of the layers that read one z as one matmul over z with the RMSNorm folded in (`_pairBias`), every layer's cond-only linears in two matmuls (`_condProj`), cycle 0's zero recycle terms skipped, feature rows padded to 32, token matmuls ordered row block fastest (`linear4x4pk-cm`), texel-wise pair write; around the triangle contraction, the gated projections computed in rows i * Kp + k and written transposed (a channel's 8 k are two texels for the transpose) and the gather writing four j-planes that the LayerNorm after it reads (`jplanes`); 4 x 8 outputs left as planes for a reader that takes them (`linear` 'planes': the transition's hidden layer as the next matmul's x, the triangle gate in `_repackResid`); z and the triangle contraction's result in float16 (`zHalf`, `xHalf`, as WebGPU's half mode holds them), which needed float16 render targets written rounded to nearest (`gl.js` `R16`): the conversion on writing truncates on an M2, and truncation's bias added up (z in float16 lost 6e-3 relative on motif_idx_1prw, 3e-4 rounded, as float32; a whole sm_sam design now ends exactly where WebGPU half's does, 1.67 A from the float32 oracle, 6 residues changed, a divergence of float16 z itself: float32 z gives 0.017 A); LayerNorms in front of a 4 x 8 matmul that reads z's planes folded into it (`_lnFold`: W' = W diag(w), the mean's term from rowsum(W'), only a statistics pass: the transition's and the recycle's); z held as packed planes in the 4 x 8 matmul's output layout (`_toZPlanes`, `zPlanes`: a residual update writes the new z in its epilogue, with no repack pass, and norms and the pair bias read half the texels); the token block fused (`_adaLNFused`, `_rowReader`, `_scaleAdd`, q/k/v/g split from the matmul's planes, SwiGLU packed from its planes) and the q/k RMS norms folded into the attention scores (`_attnFolded`); the pair write never materialised (`_pairWriteView`: the norm and the residual that read it add the outer product as they read); the heads drawn together and waited for once; to_qkv and to_g one matmul (`_stacked`); split K for token matmuls with few fragments (`linear4x4pk-cm-sk`). What a kernel costs in a real pass: `--skip=<regex>` leaves its draws out (wrong results, honest timing; the per-draw `--profile=1` syncs inflate short kernels several-fold). Tried and no faster: the output planes' texture width (48 to 768 texels: 1.48-1.55 TFLOP/s on the 4 x 8 matmul either way; which fragments run together is not this path's limit, unlike WebGPU's); a folded norm's statistics gathered in the matmul's own row walk (WebGPU's fused input norm: 1.07x slower, every column block repeats them); 2 x 2 quads of fragments sharing their fetches through derivatives (dFdx / dFdy are fine-grained here, so a fragment can read its neighbour's values: 6 texel reads per 256 multiply-adds, but 3.4x slower, `bench-webgl --quad=1`); the 4 x 8 block for token matmuls (fewer fragments at n = 100); fence polling by message-channel yields; an 8 x 8 block over eight packed targets (128 bytes a pixel: 2x slower than 4 x 8); norm statistics split over several fragments a row; weights as uniform buffers or constant-indexed uniforms (0.07-0.65 TFLOP/s against 1.3 from textures: ANGLE's constant buffers); the gated projections written straight into the batched matmul's channel-major layout (2.2x slower: neighbouring fragments then share no input rows). A microbenchmark that redraws into the same targets measures one draw, not several: the tiler's hidden-surface removal culls all but the last opaque full-screen draw of a render pass.
   - `web/`: Interactive browser studio (`index.html`, `web/app.js`, `web/studio-api.js`, `web/studio/`, `web/examples/*.cif.zst`) embedding the `nvidia/rfd4-proteina-zerogpu` / `AtomWorks Studio` interface (Mol* WebGL 3D viewer, sequence dock, condition popovers, live trajectory playback, and PDB/mmCIF/ZIP export) backed 100% client-side by WebGPU.
   - **The design card is Studio's, not this page's** (`window.atomworksStudio.mountDesignCard`; the contract, the provider and what the card needs from the server are in Studio's `docs/INTEGRATIONS.md`, "Design card"). Start screen, the job as pieces, popups, run settings, Generate and Stop, the status line, the Outputs tab with the Refold panel, Save all (.zip), the Studio-editor switch and light/dark are all Studio's (`packages/web/src/design-card/`); this page used to carry the same thing as `web/design-panel.js`, `web/design-spec.js`, `web/page/card.html` and `web/results-zip.js`, and the tests that pinned it (`design-spec`, `ligand-ccd`, `results-zip`) moved with it (`design-spec.test.ts`, `design-ligand.test.ts`, `design-zip.test.ts` there). What stays here is the engine behind the card, and it is small: `web/app.js` `Rfd4pStudioApp` (`_provider`: the engine badge, the run settings this engine takes, `generate`, LocalFold as the refold, the speed hint, the guide, the zip's refold record, weight preloading) and `web/studio-api.js`, the in-browser Studio server the card reads and edits through (`window.atomworksStudio` and `/api/*`: the same contract as Studio's Python server, which the card is tested against too). `generate(request, hooks)` reads the card's annotated input (`request.cif`, `buildBatch`), reports through `hooks` (`progress`: the Generate button, now Stop, fills with "design k of n · step s/60"; `status`; `loading`: the weights; `frame`: every step's live structure with its motif overlays and hotspots, waited for in order; `design`: the structure, its trajectory, `kind`, `designedChains` and `data` for the refold) and ends on the line the status box shows. `app.runDesign(overrides)` is the same without the card, from a bundled preset (`_loadPreset`), for the GPU gates; `app.nsteps` shortens a run (the card has no control for it). What the engine (studio-api.js, the pipeline) does that the card relies on: new residues inserted inside a chain do not renumber it (with no numbering gap the placeholder takes the residue before's number plus an insertion code, `insertSegment`, "40A", and `realizeExpandableSegments` numbers past it, so the batch and the design are numbered exactly as the old renumber-the-rest rule made them: `test/insert-numbering.test.js`), so a design numbers residues after an insertion further along than the input, and hotspots on a design are matched through each sample's batch atoms (`designHotspots`, in the viewer's numbering: its CIF's auth_seq_id and insertion code) while live frames are numbered by res_id, which never repeats in a chain (so their hotspot keys carry no insertion code); a document remembers the residues new residues replaced (`segmentOrigins`, `segmentOrigin`, `restoreSegment`, `/segments/restore`, read through `GET /segments/origins`; `test/segment-restore.test.js`) and each loaded chain as it was loaded (`chainSources`, carried by `combine` and a chain rename; `sourceResidues`, `restoreFromSource`, `/residues/restore`, `GET /chains/{cid}/source`), and can bring residues back from their source entry next to their neighbours (`/residues/insert`, `insertResiduesFrom`: one Undo, peptide and new-residue bonds rebuilt, an ordered motif's chain renumbered; `test/residue-insert.test.js`). "Rigid" is one rigid group per source structure (`/internal-coords` `group_id`: chains from the same entry share a body), and its saved targets are cleared (`/internal-coords/clear-targets`): the pipeline centres the body and turns it at random when the job is built (`materializeInternalCoords`), as AtomWorks does. A residue fixed "anywhere" with only some atoms held keeps only those atoms' coordinates, held atoms first in the residue (`/coordinates/clear`; a token is read from its first atom). Superposition (`superimposeCoords3D`) is a rotation, never a reflection (`test/handedness.test.js`): it used to mirror whenever its eigenvectors came out left-handed, and a design with nothing held in place, aligned onto its first (noise) frame, was then shown as its mirror image, every helix left-handed, about half the time. With nothing held in place, upstream leaves a design in the model's frame; the page lays it on its rigid target as loaded (`processSampleToAtoms({ inputFrame: true })`, `alignOntoRigidGroup`: the group on a chain with hotspots, else the largest), live frames and designs alike (the Cα trajectory still follows the run's first frame), and designs and live frames are put back in the input's frame (the pipeline centres the conditioned coordinates for the model and records `center_shift`; `processSampleToAtoms` adds it back after aligning), so a fetched target does not jump when a run starts. A job whose every chain keeps its backbone with its sequence free (the card's "Redesign sequence", `task.key === 'inverse'`) runs the inverse-folding sampler (`resampled_forward_marginal`), as the Space does for that task (`generation=inverse_folding`): the backbone comes back as given (Cα within 0.02 Å), only sequence and side chains sampled; partial diffusion is the card's one option on top (the percent, `partial_trajectory_fraction_steps`, 0.4 as upstream's Space runs its partial-diffusion example). The encoder treats an atom without coordinates (a side chain an entry did not resolve) as absent (`encoderSeqFeatures`), or its NaN reached every latent and partial diffusion of such an entry (6MRR) gave a design with no atoms. A plain structure (a PDB ID or file) opens with everything fixed (`StudioDoc`, rcsb preset: `test/fetch-defaults.test.js`), without buffer ions (NA, CL, on top of AtomWorks' additive list), without the residues the entry did not resolve (`removeUnresolvedResidues`; the example recipes keep them: `POST /sessions` takes `keep_unresolved`) and with its ligands' formal charges from the CCD (`componentsNeedingCcd`); a prepared document drops the file's text (`rawCif`), so its CIF, for the viewer and for a run, is the prepared one from the first frame. On desktop Chrome without subgroup matrices, the speed notice sits beside Generate (`_renderSpeedHint`, the card's `renderExtras`; Copy address, Not now) and each design's status line repeats "up to 1.5× faster" until it is dismissed. Thinking defaults to none, for speed (upstream's default is medium, `inference.yaml`; about 3x the passes). `test/doc-edits.test.js` and `test/recreate-examples.test.js` hold the document edits the card makes (one Undo each, a refused edit leaves no trace, the examples rebuilt from bare structures) against what the model reads (`test/model-read.js`); `test/design-card-routes.test.js` the read routes it uses.
   - **Chains are edited as plans** (studio-api.js `chainPlan`, `rebuildChain`, `previewRebuild`; `/chains/rebuild`; `test/chain-plan.test.js`, `test/chain-links.test.js`). A chain loaded from an entry reads as an ordered list of parts, kept runs of the chain as loaded ({ kind: 'kept', lo, hi }, consecutive in the source) and blocks of new residues ({ kind: 'new', atom | min, max }); an edit changes the list and `rebuildChain` makes the atoms from it in one step and one Undo: residues already in the chain keep their atoms and conditions, missing ones come from the chain as loaded (as loaded), new blocks get a placeholder, and then order, numbering (the source's when the parts run in its order, new blocks between as `insertSegment` numbers them; else 1, 2, 3… with each residue named by its source, "A38"), source names and bonds (consecutive source residues joined, every new block joined to both neighbours, a gap left a gap; side-chain links kept) are set by one rule. Never patch a chain's atoms step by step for an edit the plan can say (that is how a new block was left hanging from one end, a drag bar stopped at new residues, and labels switched the drag bar off). A piece's Residues (one range) and the "+" popup (New, or the entry's residues, where the "+" sits) go through it (the card's `_partsWithRange`, `_partsWithInsert`, over `GET /chains/{cid}/plan`, `POST /chains/rebuild`); while they are edited the viewer shows the chain as Apply would leave it (the card's `_previewParts`: `POST /chains/preview` on a copy drawn with `renderFrame`, the chain as loaded faint behind it, the whole chain as loaded as one faint, slightly thinner cartoon (`sizeFactor` 0.17), drawn once per popup (and again after the first frame, which loads a scene of its own) and never changed, so the residues kept hide it inside their own cartoon and only those left out show; no outline on the span being added or edited (tried as a thicker copy behind it, which read as a heavy shade, and as the selection set with each frame, which blinked on some drag steps on a real GPU; taken out at the owner's call); an overlay changed per drag step blinked, or pulsed while two were up, and one updated in place, or a lone residue, came out as solid sticks; `_endPreview` puts the document back). There are no other paths: a piece's popup takes one range (no Rest or Between; part of a piece is changed by picking it, and the example builder's `pick` step does that), "+" offers the entry's missing residues as one from – to range (the stretch missing there by default, with a drag bar; any other missing residue typed, so a motif residue removed comes back in place), and the preview of adding and of editing is the same view: what Apply keeps solid, the rest of the chain as loaded faint, nothing else (an outline drawn as a thicker copy behind the span read as a heavy shade and was taken out), and the card's selection is let go first: kept by atom index on a preview frame whose atoms are ordered differently, it picked parts of residues and Studio drew them as sticks. Every residue carries its place in the chain as loaded (`__src`, page bookkeeping, never written to the CIF and kept through Reset). Two blocks of new residues side by side share a name and a number ("98", "98A"): the pipeline's `_struct_conn` reader matches insertion codes, or both blocks' bonds landed on the second and the model read two chain breaks (`test/chain-links.test.js`).

Never edit `vendor/`; fix LocalFold and re-sync. AlphaFold 3's parameters are Google DeepMind's (non-commercial, prohibited-use policy), so the page asks once per browser before using them and offers OpenBind-0 (Apache 2.0) instead.
   - Cache-busting: `index.html` carries an import map pinning every module under `web/`, `shared/`, `webgpu/`, `cpu/` to `?v=<content hash>` (plus the `app.js` / `styles.css` tags). Run `npm run stamp` after editing any of them (`build:studio` runs it too), or browsers can mix new and cached modules for up to 10 minutes after a deploy.
   - Light and dark are the card's (`themeKey` `rfd4p.theme`: the computer's setting until ☀ / ☾ beside Guide is pressed, then that, per browser); Studio's `setTheme` switches its colours and the viewer's background. The theme is also decided in `web/page/head.html` before anything draws (on the root element, and on the body once it exists), so the page does not flash the other colour while it loads. `guide-shots.mjs` takes the guide's pictures dark (`THEME=light` for the other).
   - Chain colours come from Studio's shared palette, keyed by chain id; the card and the live sequence strip read it through `window.atomworksStudio.chainColor`. The palette (fork) is cool colours only, thirteen of them: amber is the hotspots' (`--rfd4p-hotspot`) and magenta the refold's, so neither is ever a chain's, and H, L and T fall on three different colours. Selection is one look everywhere: an outline in the text colour, no tint (fork 912934c: Mol*'s select and hover marking in the foreground colour, white on black and near-black on white, hover fainter; the sequence bar's selected residues outlined, keeping their colours, a run of them one box, fork c8d0b8c), and a sub-card holding selected residues outlined the same (`_markSelected`), so chain colours, hotspots (amber), free (accent) and the fades all still show under a selection.
   - Refold input: a refold's ONE input is a CIF made the way RFD4's AF3 oracle makes its own (`AF3Oracle._build_manifest`): the design, a user CCD defining every non-standard residue and ligand, and templates, as one multi-block mmCIF (`web/refold-input.js` reads it; `web/refold-cif.js` writes it in the browser for a design the page just made; `tools/oracle/af3_refold_input.py` writes it by running the oracle itself, and `test/refold-cif.test.js` holds the browser writer to that output on `test/fixtures/`). What makes a residue a modification of which standard one comes from the PDB dictionary's entry for it, never from a list. A refold's motif RMSDs (`web/motif-metrics.js`) follow RFD4's `refolded_motif_allatom_rmsd` and the backbone-aligned variant.
   - `tools/`: Headless Chrome WebGPU runner (`tools/gpu-chrome.mjs`), GPU differential test suites (`tools/gpu/check-{rfd4p,trunk,decoder,encoder,generate,webapp}.js`), and PyTorch oracle verifiers (`tools/oracle/check-{batch,features,sampler,cpu-trunk,decoder,encoder,output}.mjs`).
   - `test/`: Deterministic Node unit tests (`npm test`).

## WebGPU & Numerical Invariants

1. **Differential Verification**:
   - Every WebGPU kernel and network layer in `webgpu/rfd4p/` must be verified against the PyTorch oracle dumps and `cpu/rfd4p/` via `npm run test:gpu` (`DISPLAY=:99 node tools/gpu-chrome.mjs tools/gpu/check-rfd4p.js`).
2. **No `O(L^3)` Materialization**:
   - Triangle multiplicative updates (`tri_mult_out`, `tri_mult_in`) contract over `k` inside registers in the WGSL shader and never allocate `L x L x L` buffers.
3. **Guarded 2D Workgroup Dispatches**:
   - Any folded 1D workgroup index (`wid.x + wid.y * 65535u`) must check `< totalWorkgroups` before reading or writing storage buffers.
