Operational guide for coding agents working in `rfd4p` (WebGPU implementation of `RosettaCommons/RFD4-Proteina`, inspired by `../localfold`).

## Architecture & Module Layout

1. **Plain ES Modules Only**:
   - All JavaScript files must be standard ES modules loadable directly by the browser without a bundler or compiler.
   - Always include explicit `.js` file extensions in relative `import` specifiers.
2. **Directory Structure**:
   - `shared/rfd4p/`:
     - `encoding.js` & `conditions.js`: 147-token `UNIFIED_ATOM37_ENCODING` vocabulary, atom37 layouts, and condition / CATH enums.
     - `pipeline/`: Pure-JS input transform pipeline (`buildBatch` in `pipeline/index.js`) with Zstandard `.cif.zst` frame decompressor (`zstd.js`), mmCIF/PDB/annotated-CIF parser + WL entity hashes (`cif.js`), YAML/JSON condition-spec & `sel(...)` query evaluator (`spec.js`), 3D/topological stereochemistry (`chirality.js`), token bond graph & BFS path lengths (`bonds.js`), and validation transforms (`transforms.js`).
     - `features.js`: Upstream feature factories (`trunkSeqFeatures`, `trunkCondFeatures`, `pairFeatures` with static cache, `pairCondFeatures`).
     - `flow.js` & `partial.js`: Flow-matching schedules (`scheduleTsrSafe`, `noiseSchedule`, `recycleDepths`), Euler/SDE `simulationStep`, partial diffusion (`corruptBatch`, `buildPartialSchedule`), and inverse folding (`RESAMPLED_FORWARD_MARGINAL`).
     - `output.js`: Rectangular Hungarian linear sum assignment (`linearSumAssignmentMaximize`), unindexed motif insertion (`buildPredictedInsertionMapping`), internal-coordinate group grafting (`insertInternalCoordConditionedGroups`), input-frame Kabsch alignment (`alignAtomsToInputFrame`), `processSampleToAtoms`, and `toCifString` / `toPdbString`.
     - `safetensors.js` & `presets.js`: Zero-copy `parseSafetensors`, streaming + Cache API `fetchSafetensors` and `fetchShardedWeights` (keeps the int8 shard bytes; each tensor's `.data` decodes on read, so read large weights once, at GPU upload), and 10 interactive benchmark presets (`RFD4P_PRESETS`).
   - `cpu/rfd4p/`: Deterministic float32 CPU reference implementations (`trunk.js`, `decoder.js`, `encoder.js`, `reference.js`).
   - `webgpu/rfd4p/`: Recorded-command-list WebGPU engine (`engine.js` with `64x128` and `32x64` bank-conflict-free `vec4` GEMMs, `16x16` `triGate`, 64M-float triangle chunking, and FP16 weight packing), shared token blocks (`blocks.js`), `Rfd4pTrunkGpu` (`trunk.js`), `Rfd4pDecoderGpu` (`decoder.js`), `Rfd4pEncoderGpu` (`encoder.js`), and `Rfd4pGeneratorGpu` (`generate.js`).
   - `web/`: Interactive browser studio (`index.html`, `web/app.js`, `web/studio-api.js`, `web/studio/`, `web/examples/*.cif.zst`) embedding the `nvidia/rfd4-proteina-zerogpu` / `AtomWorks Studio` interface (Mol* WebGL 3D viewer, sequence dock, condition popovers, live trajectory playback, and PDB/mmCIF/ZIP export) backed 100% client-side by WebGPU.
   - `web/design-spec.js` (pure: task, chain roles, lengths and contig read from a document's conditions; tested in `test/design-spec.test.js`) and `web/design-panel.js` (start screen, Design panel, guided set-ups, simple/advanced switch). The panel lists each chain piece by piece in contig order (`designSpec(...).chains[].pieces`): `kept` (with a keep mode from `KEEP_MODES`: all, sequence, backbone, side chains, shape only; `anywhere` when unindexed; `source` when a set-up renumbered it), `designed` (in place) and `new` (a length range). Chains are grouped by where their coordinates come from (`_sourceGroups`: "PDB 1QJG", "PDB 5O45 chain A", "Nanobody (VHH) example"), one muted caption per source; clicking a caption opens the + pdb form to replace that source's chains; chains made here (+ seq, + lig) sit last, uncaptioned. Each piece is a sub-card in its chain (chain letter on the left; the chain's × there once it has more than one item), residues (or a new piece's length) on the left and its state on the right ("A17–131 · fixed · 3 hotspots", "H99–109 · designed", "50–120 · new"), its own × to remove it; a "+" between sub-cards (not next to new residues) inserts 5–10 new residues there. Clicking a sub-card opens one popup: the residue range (with a property changed, the change applies to those residues only; with nothing else changed, the piece becomes that range and the residues cut off are designed, so a loaded protein gets its fixed regions by narrowing), and three properties with one vocabulary, Structure (fixed, fixed but can move, designed) with the Atoms it holds (all, backbone, side chains, or named: "CG, OD1"), Sequence (fixed, designed) and Position in chain (fixed, anywhere); with both designed, Position gives way to Length, and a length other than the residue count turns them into new residues (`/segments/replace`). Then Hotspots (the chain's, from any of its pieces; a residue may name its atoms, "A56(CG,OH)", `parseResidueList`) and Keep only (the motif set-up, `/segments/scaffold`; the residues are kept in the order typed, "A38, A14, A99" reorders the motif and renumbers the chain as AtomWorks does, `_orderMotif`; the kept residues take the popup's properties, so trimming an antibody chain and making it "fixed, can move" is one popup). "Fixed, can move" is one rigid group per chain (`/internal-coords` `group_id`, `_rigidGroup(chain)`), so an antibody's light and heavy frameworks move apart and a framework split by CDRs moves as one, and its saved targets are cleared (`/internal-coords/clear-targets`): the pipeline centres the body and turns it at random when the job is built (`materializeInternalCoords`), as AtomWorks does and the bundled examples are saved. A residue fixed "anywhere" with only some atoms held keeps only those atoms' coordinates, held atoms first in the residue (`/coordinates/clear`; a token is read from its first atom), as an enzyme benchmark's catalytic tips are given. The chain letter opens the chain's popup: its name (`/chains`) and its place in the job (`/chains/order`), which the model reads (chain and molecule ids, noise draws). Residues selected in the viewer or the sequence bar open the same popup for the selection (`_renderPop`): the three properties ("mixed" where the selected pieces differ, left as each piece has it), Length for one designed stretch, Hotspot, a ligand's pose, and Delete / Keep only, so fixed regions are grown, shrunk, freed or cut from the structure itself; several pieces change in one edit (`_applyPieces`), one Undo. Ligands: pose fixed or free, swap. New residues: length. Popups close with Cancel, Escape or a click outside, never a ×. New residues inserted inside a chain do not renumber it: with no numbering gap the placeholder takes the residue before's number plus an insertion code (`insertSegment`, "40A"), and `realizeExpandableSegments` numbers past it, so the batch and the design are numbered exactly as the old renumber-the-rest rule made them (`test/insert-numbering.test.js`). A design therefore numbers residues after an insertion further along than the input; hotspots on designs are matched through each sample's batch atoms for that reason. A plain structure (PDB ID, optionally with the chains to keep, "1J79 A C E"; a file; "+ pdb") opens with everything fixed, without buffer ions (NA, CL, on top of AtomWorks' additive list) and with its ligands' formal charges from the CCD (RCSB entries list their components' atoms without charges, `componentsNeedingCcd`) (`StudioDoc`, rcsb preset; `test/fetch-defaults.test.js`), so a set-up starts from what was loaded and marks what to design; Keep only takes the popup's Structure, Atoms and Position (CG, OD1 + anywhere is an enzyme site), and ticking partial diffusion with nothing designed frees every chain. Start-screen examples are recipes (`TASKS[].recipe`): each fetches its PDB entry (5O45, 1XVA, 1QJG, 1J79, 1N8Z, 4Z18 + 3EAK, 2KL8, in label numbering; an entry's chains come from its first biological assembly that has them, `_openEntry`) and reproduces the bundled Studio example of the same name in everything the model reads (batch features compared tensor by tensor; the antibody and motif are identical; both 2KL8 examples keep residues 1–79 (all of it but the His tag), where the bundled file drops 8–27, a bug in it; the rest differ only where the bundled file's coordinates did not come from the deposited entry: the binder's rebuilt side chains, the SAM conformer, the nanobody framework's saved orientation, and 0.001 Å rounding in the enzyme) and builds the set-up with the card's own controls in a session Studio does not show (`_buildRecipe`: `buildSession`, whose edits go straight to `handleStudioApiRequest`, so the viewer is not redrawn per step; popups hidden by `body.rfd4p-building`), then opens it once, finished, with no Undo history; offline, the bundled Studio example opens instead ("Protein from scratch" always does). Source captions read "PDB 5O45 · A" (entry and its chains in the job; the entry's `_struct.title` when pointed at). Designs and live frames are put back in the input's frame (the pipeline centres the conditioned coordinates for the model and records `center_shift`; `processSampleToAtoms` adds it back after aligning), so a fetched target does not jump when a run starts. During a run the hotspot highlight follows the job's numbering (`app.liveHotspotKeys`, res_id past any new residues), since live frames are numbered that way. Otherwise hotspots are highlighted in the viewer by `auth_seq_id`, which is how the document's CIF numbers residues for Mol* (a fetched entry keeps its authors' numbering there; `res_id` is the label numbering). There are no separate guided set-ups; partial diffusion is a line in the run settings. Hotspots are a chip on a kept piece (`parseResidueList` / `formatResidueList`). Ligands are added ("+ lig") or swapped (a ligand's Edit menu) by their CCD code: `web/ligand-ccd.js` turns the dictionary entry's ideal coordinates into a one-residue mmCIF, merged in with its pose free. "+ seq", "+ pdb" and "+ lig" add a designed chain, chains from a PDB entry or file, or a ligand; merged in as kept chains through `/combine` (a source caption replaces that source instead), so an example is edited the same way a set-up is built from scratch. The panel edits documents only through `window.__rfd4pMutate`, so Undo and Studio refreshes work as for Studio's own edits.
   - AtomWorks Studio is **not vendored**. `studio.json` pins the release; `npm run build:studio` downloads that bundle, verifies its sha256, copies it into `assets/` and composes `index.html` from Studio's own page plus the two fragments this repo owns (`web/page/head.html`, `web/page/card.html`). Never hand-edit `assets/` or `index.html` — both are build output. Live frames, overlays, sessions, edits, the selection, chain colours and live mode go through Studio's documented embedding API, `window.atomworksStudio`. To try an unreleased Studio: `npm run build:studio -- --from <path-to-bundle>`. **Right now the site runs an unreleased Studio**: `studio.json` `override` names the commit (sokrypton/atomworks-studio `live-frame-cartoon`: cartoon overlays, RosettaCommons/atomworks-studio#29, live frames drawn as cartoon plus ligands, `setHighlight`, which the panel uses to colour hotspots in the target's own cartoon, and Show/Hide sequence in the viewer toolbar with no sequence-dock heading), and `build:studio` refuses a plain release rebuild until `override` is removed after a release contains it.
   - Refold (`web/refold-view.js`, the Refold row under a finished design): LocalFold's `refoldDesign` refolds the design's sequence with AlphaFold 3 (the default) or OpenBind-0 (kept chains as templates), and the refold's designed chains are overlaid as a magenta backbone trace. That code is **vendored, not written here**: `localfold.json` pins a `sokrypton/localfold` commit, and `npm run sync:localfold [<commit>]` copies the import closure of its entries into `vendor/localfold-<commit>/` (the commit in the path is the cache-busting) and rewrites `web/localfold.js`. Never edit `vendor/`; fix LocalFold and re-sync. AlphaFold 3's parameters are Google DeepMind's (non-commercial, prohibited-use policy), so the page asks once per browser before using them and offers OpenBind-0 (Apache 2.0) instead.
   - Cache-busting: `index.html` carries an import map pinning every module under `web/`, `shared/`, `webgpu/`, `cpu/` to `?v=<content hash>` (plus the `app.js` / `styles.css` tags). Run `npm run stamp` after editing any of them (`build:studio` runs it too), or browsers can mix new and cached modules for up to 10 minutes after a deploy.
   - Chain colours come from Studio's shared palette, keyed by chain id; the design panel reads it through `window.atomworksStudio.chainColor`.
   - `tools/`: Headless Chrome WebGPU runner (`tools/gpu-chrome.mjs`), GPU differential test suites (`tools/gpu/check-{rfd4p,trunk,decoder,encoder,generate,webapp}.js`), and PyTorch oracle verifiers (`tools/oracle/check-{batch,features,sampler,cpu-trunk,decoder,encoder,output}.mjs`).
   - `test/`: Deterministic Node unit tests (`npm test`).

## WebGPU & Numerical Invariants

1. **Differential Verification**:
   - Every WebGPU kernel and network layer in `webgpu/rfd4p/` must be verified against the PyTorch oracle dumps and `cpu/rfd4p/` via `npm run test:gpu` (`DISPLAY=:99 node tools/gpu-chrome.mjs tools/gpu/check-rfd4p.js`).
2. **No `O(L^3)` Materialization**:
   - Triangle multiplicative updates (`tri_mult_out`, `tri_mult_in`) contract over `k` inside registers in the WGSL shader and never allocate `L x L x L` buffers.
3. **Guarded 2D Workgroup Dispatches**:
   - Any folded 1D workgroup index (`wid.x + wid.y * 65535u`) must check `< totalWorkgroups` before reading or writing storage buffers.
